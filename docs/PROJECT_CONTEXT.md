# 아산시 버스 통합 노선도 프로젝트 — 컨텍스트 문서

작성일: 2026-11-17. 갱신: 2026-11-18(선형 꼭짓점 순서 결함 보정, 시 전체 노선망 첫 시각화, 시 전체 유향 그래프·MariaDB 스키마·적재 파이프라인, 저장소 구조·`.env` 설정·웹용 데이터 단계 결정, `core.geo`·`core.groups` 통합, 수집 실패 재시도·적재 차단). Claude Code 작업 규칙은 저장소 루트 `CLAUDE.md`에 있다. 이 문서는 첫 대화에서 확정한 내용, 데이터로 검증한 사실, 미해결 과제를 새 대화에서 이어가기 위해 정리한 것이다.

## 1. 프로젝트 목표

중소도시 노선버스는 같은 방면으로 가도 경유지가 다르면 번호가 나뉘고 도착정보도 따로 나온다. 이 프로젝트는 아산시 버스정보시스템(bus.asan.go.kr) 데이터를 이용해 **번호가 아니라 실제로 다니는 길을 기준으로 노선을 합쳐서 보여 주는 서비스**(통합 노선도, 통합 도착정보, 실시간 위치)를 만든다.

- 서버: Raspberry Pi 5, Ubuntu 24.04
- 스택: React + FastAPI
- 성격: 개인 토이프로젝트. UI 표기법은 배포 단계에서 다루기로 하고 지금은 그래프 구조에 집중한다.

## 2. 핵심 결론

1. **도로 그래프 방식이 맞다.** 노선 선형 좌표(`shape`)를 도로로 삼아 그래프를 만들고 그 위에 정류소와 노선을 얹는다. 정류소 순서 기반 그래프는 가짜 분기가 많아 폐기했다.
2. **서비스의 기본 단위는 번호 계열이 아니라 구간(서비스 구간)이다.** 번호 계열과 실제 방면이 일치하지 않는 사례가 영인 구간, 온양~배방 구간, 800번대에서 확인됐다. 사용자도 이 방향에 동의했다.
3. **그래프는 계열별이 아니라 시 전체로 한 번 만들어야 한다.** 계열·방면은 그 위에서 일부를 잘라 보는 보기(view)다.
4. **모든 노선은 방향별 편도로 저장하고 키는 `route_id`다.**

## 3. 데이터 소스 (API)

아산시 버스정보시스템 웹 화면이 호출하는 내부 API다. 공공데이터포털에는 없어 현재 유일한 수단이다. 상세 명세는 별도 문서 "아산시 버스정보시스템 API 명세"(Claude Doc)에 있다.

- 기본 URL: `https://bus.asan.go.kr/mobile/traffic/{엔드포인트}`
- 전부 POST, `application/x-www-form-urlencoded`. 인증·쿠키 없음.
- 캡처된 헤더: `X-Requested-With: XMLHttpRequest`, `Origin`, `Referer: https://bus.asan.go.kr/web/traffic_total_search`
- 응답은 JSON이고 모든 값이 문자열이다. 무관한 필드는 `""`로 채워진다. 값 끝에 공백이 붙는 경우가 있어 trim이 필요하다.

| 엔드포인트 | 파라미터 | 내용 |
| --- | --- | --- |
| `searchBusRoute_1` | `busRouteType=` (빈 값 = 전체) | 전체 노선 목록 327건 |
| `searchBusRoute` | `busRoute` | 노선번호 부분 일치 검색 |
| `selectBusRoute` | `busRouteId` | 노선 1건 |
| `searchBusRouteMap` | `busRouteId` | 정류소 순서(`busRouteDetailList1`), 선형 좌표(`busRouteDetailMapVoList`) |
| `searchBusTimeList` | `busRouteId`, `weekcd=1` | 기점 출발시각 목록과 평일·토·공휴일·방학 운행 플래그 |
| `searchBusStopAll` | `minLat`, `maxLat`, `minLng`, `maxLng` | 범위 내 정류소 |
| `searchBusStop` | `busStop` | 정류소 단축번호 검색 |
| `searchBusRealLocationDetail` | `busRouteId` | 노선별 운행 차량 위치 (공식 화면은 3초 간격 호출) |
| `searchBusStopRoute` | `busStopId` | 정류소 도착정보. 경유 노선마다 1건 |

### 데이터 주의사항

- **`route_id`는 노선의 한 방향이다.** 상행과 하행은 다른 `route_id`다. 한 방향만 있는 노선명이 49개다.
- **`route_name`은 키가 아니다.** 같은 번호가 천안 노선과 아산 공영버스에 중복된다.
- **`route_type`**: 102 일반 시내버스(167건), 101 공영버스(122건), 103 순환(2건, 순환5), `13 `(공백 포함) 천안 노선(36건, 제외 대상).
- **천안 제외는 `route_type`으로 한다.** 900·910번은 `route_id`가 285로 시작하지만 아산 노선이다. 천안 3사와 아산 2사의 1:1 공동배차다.
- **차량 소속은 `veh_id` 앞 3자리**로 구분된다. 285 = 천안 면허(충남70자), 288 = 아산 면허(충남72자, 1000번대 온양교통, 1100번대 아산여객). `veh_id` 끝 4자리가 번호판 숫자다.
- **`stop_id`는 방향별로 다르다.** 맞은편 정류소는 다른 ID다. 예외로 단방향 루프 구간은 상하행이 같은 `stop_id`를 쓴다(소화마을 구간).
- **`busRouteDetailList1`의 마지막 원소는 정류소가 아니라 노선 요약 레코드**다(`stop_ord`가 빈 값).
- **선형 꼭짓점 순서 결함(2026-11-18 확인)**: 크롤러는 `(route_ord, ord)`로 정렬하고 있으나, 원본 데이터 자체에 일부 링크의 꼭짓점이 역순으로 들어 있다. 같은 직선 위에서 앞뒤로 왔다 갔다 하는 지그재그(U턴 2회 이상이 몇 점 안에 몰림)로 나타나며, 그래프에서는 정류소 없는 가짜 루프가 된다. `fix_shape.py`가 양 끝 기준점 사이 직선에 투영한 순서로 재정렬한다(직선에서 30m 넘게 벗어나는 점이 있으면 실제 회차로 보고 두지 않음). 보정 후 정류소 투영 거리·순서가 나빠진 노선은 없다. 보정 내역은 출력 JSON `meta.shape_fixes`에 남는다.

  | 위치 | 노선 (`route_id`) | 제거된 가짜 거리 |
  | --- | --- | --- |
  | 이순신고 ~ 쌍용동일아파트 (온천대로 동쪽) | 900 상행(285000245), 910 상행(285000249), 2000(288000359) | 약 1.0km |
  | 배방 127.082 부근 | 840(288001040), 2000(288000359) | 약 0.5km |
  | 시외버스터미널 건너 ~ 아산소방서 건너 | 850(288000095), 링크 2개가 중복 삽입 | 약 1.5km |
  | 소규모(30~40m) | 240, 63, 63-1, 63-3, 63-4 | — |

  재수집 시 매번 다시 적용해야 한다(크롤 → `fix_shape.py` → 그래프 빌드).
- **위치 API 좌표 결함**: 정차 중인 차량 일부는 `lng`에 `lat` 값이 들어온다. 위치는 GPS가 아니라 `stop_id`(최근 정류소)로 잡는다.
- **도착정보**: 남은 시간·정류소 수가 문자열이다(`약3분후`, `2구간전`, `HH시 MM분 출발 예정`). `provide_code` 3 = 운행 중, 1 = 출발 전. 노선당 1대만 나온다.
- **`route_direction` 값을 믿을 수 없다.** 615, 660, 303, 304번은 상행으로 등록되어 있지만 도심행이다. 방향은 "도심 쪽이 기점인지 종점인지"로 직접 판정해야 한다.
- **`turn_useflag=1` 노선(10건)도 정류소 순서는 평범한 편도**다. 별도 처리가 필요 없다.
- **시간표 건수와 `alloc_time`이 다른 노선이 있다.** 원인 확인(2026-11-18): 82-1번(288001019)은 완전히 같은 행이 2번 들어 있다. 88-1번(288001021)은 ord 1~5(1010~1750)와 ord 1~7(0930~1720) 두 묶음이 섞여 온다. **API의 시간표 `ord`는 유일하지 않다.** 빌더는 같은 행을 하나로 줄이고 `seq`를 새로 매기며 원본은 `src_ord`로 둔다. 88-1의 두 묶음 중 어느 쪽이 맞는지는 여전히 미확인이다.
- **정류소가 선형 밖에 있는 노선(선형 누락 의심)**: 650번(동정리 일대, 최대 2.0km), 700·702번(퓨전빌 기숙사·명암3리, 약 300m), 41-1·46-1·46-2·47번(삼실이, 약 200m). 들어갔다 나오는 꼬리 구간이 선형에서 빠진 것으로 보인다. 빌더는 `snap_dist_m`으로 남기고 100m 초과는 검증 경고로 출력한다.
- **시간표는 기점 출발시각만 준다.** 중간 정류소 시각은 없다.
- 아산시 시내버스는 대부분 평일·토·공휴일 공통 시간표다. 요일 구분 로직은 만들어 두기로 했다.

## 4. 아산시 노선 체계 (사용자 제공 도메인 지식)

| 번호대 | 방면 | 비고 |
| --- | --- | --- |
| 100 | 송악 | 120은 유구터미널까지 감 |
| 200 | 성환 | |
| 300 | 신창(면사무소)·선장 | 340은 사실상 별도 노선. 350·351·352는 별도 계통. 본계통은 340 미만 |
| 400 | 신창(읍내)·도고·선장 | 400·430·450이 핵심 |
| 500 | 평택 | |
| 600 | 염치·영인·인주 | |
| 700 | 탕정 | 미분석. 복잡함 |
| 800 | 배방 | 권역도 방면도 맞지 않음. 미분석 부분 많음 |
| 900 | 천안 | |
| 1000 이상 | 특화 노선 | 미분석. 2000번은 순천향대 ↔ 평택지제역 |

- **두 자리 수 노선은 시 소속 공영버스**이며 같은 십의 자리의 백번대와 같은 방면이다(10번대 = 100번대, 60번대 = 600번대).
  - **예외(데이터 확인)**: 20번대(20·21·22·23)는 성환이 아니라 송악 쪽(강장리, 공설봉안당)으로 간다. 10번대 중 10번(Y시티 → 불당)도 송악 방면이 아니다. 십의 자리 규칙은 기본값일 뿐이고 관리자 테이블에서 덮어써야 한다.
- **한 자리 수 노선은 시내만 다니는 공영**이며 거의 등교 전용이다.
- **공영버스는 시골 구간만 정차하고 시내버스 정차 구간은 무정차로 통과한다.** 도로는 같이 지나되 서지 않는 "급행 지선"으로 본다. 41번처럼 신창역을 경유하는 예외가 있다.
- **등교 노선**은 일 1회 편도이며 경로가 다르다. 405번(순천향대 → 온양터미널, 중고교 경유), 151번, 303·304번(도심행 편도 1회)이 해당한다.
- 통상 00으로 끝나는 번호를 본선이라 부르지만, 이 프로젝트에서 본선은 "많은 노선이 겹쳐 지나가는 구간"이다.

## 5. 확정된 설계 결정

### 저장

- 키는 `route_id`. `route_name`은 표시용.
- 천안 노선(trim 한 `route_type`이 `13`)은 제외. 291건이 남는다.
- 왕복 노선도 상행·하행을 각각 독립된 편도 노선으로 저장한다.
- 요일 구분 로직 유지(시간표의 운행 플래그 4종 저장).
- 계열 소속은 코드가 아니라 DB 테이블(`route_id` → 계열)에 둔다. 번호 규칙으로 기본값을 채우고 관리자가 덮어쓴 값이 우선한다. 계열 간 겹침, 등교 노선 포함 여부, 손님 노선은 관리자 영역에서 수동 처리한다.

### 수집

- 정적 수집: `searchBusRoute_1` 1회 + `route_id`마다 `searchBusRouteMap`, `searchBusTimeList`. 전체 약 583회. 월 1일 무렵 정기 실행 + 수동 실행(월중 시간표 변경 등)이며, 수동 실행도 전체를 다시 받는다. 이전 상태와의 비교는 ④의 `data_hash`로 한다(같으면 적재 안 함).
- 수집 실패: 요청마다 3회 재시도, 전체 순회 뒤 실패 노선만 60초 뒤 한 번 더 받는다. 남은 실패는 `meta.errors`에 기록되고 ③이 치명적 이슈 `수집 실패`로 올려 ④ 적재를 막는다. `--retry <raw.json>`으로 실패 노선만 다시 받아 그 파일을 갱신한다(노선 목록은 다시 받지 않음). 일부 노선만 받는 갱신은 노선 목록 변화를 놓치므로 두지 않는다.
- 출력: `--out`을 생략하면 `data/snapshots/<YYYY-MM-DD>/raw.json`, 같은 날 이미 있으면 `<날짜>_2`, `_3` … 폴더에 쓴다.
- 수집 직후 `fix_shape.py`로 선형 꼭짓점 순서 결함을 보정한다.
- 실시간: 클라이언트는 시청 서버를 직접 호출하지 않는다. 서버가 대신 호출해 캐시한다.
- 캐시 단위는 위치가 `route_id`, 도착정보가 `stop_id`. 유효시간 5~10초. 그 안의 같은 요청은 캐시로 응답한다.
- 사용자가 보고 있는 계열·정류소만 폴링한다.
- 시간표상 운행 중일 수 없는 `route_id`는 폴링하지 않는다. 판정 구간은 "첫 출발시각 ~ 마지막 출발시각 + 운행 소요시간"으로 제안했고(미확정), 소요시간은 초기 고정값 후 관측치로 대체한다. 자정을 넘는 노선(심야2 등)을 고려한다.

### DB와 수집 파이프라인 (2026-11-18 확정)

- DB는 **MariaDB**(사용자에게 익숙한 MySQL 문법). Ubuntu 24.04 기본 패키지 10.11 LTS. 그래프 탐색은 DB가 아니라 FastAPI 기동 시 메모리에 올려 Python에서 한다. DB는 기준 원본 저장소.
- 파이프라인: ① 수집(`crawl_asan.py --series all`, 원본 JSON 보관) → ② 보정(`fix_shape.py`) → ③ 빌드·검증(`build_city_graph.py`) → ④ 적재(`load_graph.py`). 월 1일 무렵 정기 실행 + 수동 실행.
- **변경 감지**: 노선마다 `geom_hash`(선형·정류소), `timetable_hash`, `info_hash`를 두고 전체를 `data_hash`로 묶는다. 활성 버전과 같으면 적재하지 않는다(데이터 수정 없음). 다르면 무엇이 바뀌었는지 출력하고 새 버전으로 통째로 넣는다(시간표만 바뀌어도 새 버전, 단순함 우선).
- **버전 전환**: 모든 그래프·노선·정류소·시간표 테이블이 `version_id`를 가진다. 새 버전을 `loading → ready`로 넣은 뒤 `current_version` 한 행만 바꿔 전환한다. 조회는 활성 버전만 보이는 `v_*` 뷰로 한다. 기본 3개 버전 보관(롤백 = `current_version` 되돌리기).
- **안정 ID**: `node_id`는 좌표 해시, `segment_id`는 점열 해시(63bit 정수). 재빌드해도 안 바뀐 점·구간은 ID가 유지된다. 관리자 입력(`route_group_override`)은 버전과 무관하게 `route_id`에만 연결한다.
- **필터(노선별·권역별 표시)**: `route_segment`(노선 → 구간 순서)로 노선별, `v_route.group_code`(기본 계열, 관리자 덮어쓰기 우선)로 권역별, `segment.geom` SPATIAL INDEX로 지도 범위별 조회가 된다. MariaDB 10.11에서 시험 완료.

### 저장소 구조와 설정 (2026-11-18)

- 파이프라인 코드는 `core/` 패키지(`crawl/`, `graph/`, `db/`, `config.py`), 실험·분석 코드는 `analysis/`, 데이터는 `data/snapshots/<날짜>/`(git 제외). 프로젝트 루트에서 `python -m core.<모듈>`로 실행한다.

### 웹 렌더링 데이터 (2026-11-18 구현)

- DB 적재·전환 뒤 ⑤단계에서 **활성 버전을 DB에서 읽어** 웹용 정적 파일을 만든다: `network.<hash>.json`(구간 좌표 3m 단순화), `routes.<hash>.json`(노선 → 구간 순서, 정류소, 계열), `stops.<hash>.json`, `manifest.json`. 해시 파일명으로 캐시 문제를 없애고 nginx가 바로 서빙한다.

- **구현**: `core/web/export.py`가 활성 버전 뷰를 읽어 `frontend/public/data/`에 쓴다. 좌표는 `core.geo.xy` 평면 m 정수(원점 36.78N 127.0E), 구간 좌표 RDP 3m(`core.geo.simplify`) → 13,830점. 실측: network 414KB(gzip 142KB), routes 261KB(36KB), stops 147KB(34KB). network가 예상보다 큰 것은 문자열 ID·노선 색인을 함께 넣었기 때문이다. 출력은 결정적이라 같은 활성 버전이면 해시 파일명이 같다.
- **뷰어**(`frontend/`, Vite + React JS, 배경 지도 없는 SVG): 휠·버튼 확대, 끌어서 이동, 더블클릭 전체 보기. 기본망은 운행횟수 √ 굵기의 회색 선.
  - 권역 선택(복수): 선택 계열 노선이 지나는 구간만 계열 색으로 강조, 굵기는 그 계열 운행 합 √. 공영 제외 옵션. 선택 부분 그래프의 분기(out>1)·합류(in>1) 점과 요약(구간, 총연장, 분기·합류 수).
  - 권역 노선 목록: 권역을 고르면 그 계열 노선 카드(번호, 기점↔종점, 평일 운행 합, 공영 표시)가 검색 없이 뜬다. 시내·순환을 먼저, 공영을 뒤에 둔다. 누르면 선택·해제되고, 마우스를 올리면 지도에 검은 선으로 미리 보인다. 권역을 여러 개 고르면 계열별 소제목으로 나뉜다.
  - 노선 선택(번호 부분 일치 검색, 복수): 노선명마다 색, 상·하행(route_id)별 켜고 끄기, 표기는 "기점 → 종점". 진행 방향 화살표, 정류소(확대 시 중간 정류소·이름), 평일 운행·첫차·막차·정류소 수·길이.
  - 겹치는 줄은 진행 방향 오른쪽으로 차례로 쌓는다. 유향 그래프라 상·하행 구간이 도로 양쪽으로 갈라져 보이고, 같은 구간을 지나는 노선이 나란히 놓여 400·430·450의 단축·연장 관계가 드러난다.
  - 선택 상태는 URL 해시(`#g=4,6&r=450&p=1&n=0`)에 남는다. 모바일 폭(720px 이하)은 지도 위·패널 아래 배치.
  - 한계: 구간 툴팁은 가운데 선 기준이라 오프셋된 줄 위에서는 옆 구간이 잡힐 수 있다. 개요용 무방향 도로축은 아직 없다.

## 6. 도로 그래프 방법론

### 검증된 사실

- **같은 도로를 지나는 노선은 선형 좌표가 소수점까지 동일하다.** 400번 상행 좌표 148개가 전부 430번 상행에 들어 있다. 근접 매칭 없이 좌표 일치만으로 도로가 합쳐진다.
- **상행과 하행은 좌표가 겹치지 않는다**(단방향 루프 구간 제외). 방향별로 그래프를 따로 만든다.
- **정류소는 도로에 정확히 얹힌다.** 정류소에서 도로까지 거리의 중앙값이 1~3m다.
- **교차로 보정이 필요하다.** 교차로에서는 노선마다 좌표가 몇 m 어긋나 10m 안팎의 가짜 구간이 생긴다. 30m 미만 구간의 점들을 한 점으로 합친 뒤 다시 빌드한다.
- 연속 중복 좌표(도로 링크 경계)는 제거한다.
- **선형에 역순 링크가 섞여 있을 수 있다**(3장 참고). 그래프 빌드 전에 보정한다.

### 3층 구조

1. **도로 층**: 점 = 좌표, 간선 = 연속한 두 좌표. 기종점·분기·합류·노선 집합이 바뀌는 점을 분기점으로 삼고, 그 사이를 도로 구간(segment)으로 압축한다. 구간 가중치는 지나는 노선의 일 운행횟수 합이다.
2. **정류소 층**: 정류소를 자기 노선의 선형에 순서대로 투영해 (구간 id, 구간 내 거리)로 붙인다.
3. **노선 층**: 노선마다 지나는 구간 목록(`segment_path`)과 정차 정류소 목록을 가진다. 무정차 통과는 "구간은 지나되 정류소 목록에 없음"으로 표현된다.

### 본선과 가닥

- **공통 본선**: 운행횟수가 가장 많은 구간에서 양쪽으로 가장 굵은 구간을 따라가되, 최대치의 60% 아래로 떨어지면 멈춘다.
- **가닥(strand)**: 공통 본선과 도심 쪽에서 만나는 길이 같은 노선들의 묶음. 상행은 본선에 들어오기 직전 구간, 하행은 본선에서 나간 직후 구간이 같은 노선끼리 묶는다. 기점 정류소 이름으로 묶는 방식은 600번대에서 깨져서 폐기했다.
- 한계: 400번대 하행에서 402·404와 406·407이 한 가닥으로 묶인다. 가닥 안에서 한 번 더 나누는 단계가 필요하다. 다발형 계열(900번대)에서는 공통 본선이 마지막 0.5km뿐이라 이 분류가 의미가 없다.

### 구조 유형 6가지

| 유형 | 설명 | 예 |
| --- | --- | --- |
| 단축·연장 | 같은 길 위에서 일찍 끝나거나 더 감 | 400 / 430 / 450 / 451 |
| 분기 | 한 지점에서 갈라져 돌아오지 않음 | 건널목삼거리의 430 / 450·451, 오목오거리 입구의 301·310 / 320 |

| 가지끼리 재합류 | 서로 다른 가지가 다시 만남 | 311번이 선장사거리에서 320번대와 합류(상행만) |

### 계열의 모양 2종

- **발산형**(300·400·600번대): 도심 공통 구간에서 외곽으로 갈라진다. 트리로 그린다.
- **다발형**(900번대): 양 끝이 모두 도시이고 가운데가 여러 갈래다. 갈래를 나란히 놓는 표기가 맞다.

### 시 전체 유향 그래프 (DB 기준 그래프) — 2026-11-18

`build_city_graph.py`. 기존 `build_road_graph.py`의 방식(좌표 일치 + 30m 미만 무정차 구간 합치기)을 시 전체 291개 노선(상·하행, 시내·공영·순환 전부)에 한 번에 적용한다. 상·하행은 좌표가 겹치지 않으므로 방향을 나누지 않고 그래프 하나에 넣는다. 본선·가닥 판정은 하지 않는다(보기 단계의 분석).

- 결과: 구간 1,633개, 노드(분기점) 1,055개(분기 524, 합류 520), 정류소 2,271개, 노선-정류소 11,475건. 정류소 투영거리 중앙값 1.9m. 노선 경로 끊김 0건.
- 정류소 합치기 보호: 정류소가 얹히는 선분이 있는 짧은 구간은 합치지 않는다.
- 출력 JSON이 DB 테이블과 1:1로 대응한다(`nodes`, `segments`, `stops`, `routes`, `route_segment`, `route_stop`, `timetable`, `graph_hash`, `meta.issues`).

### 시 전체 노선망(무방향, 시각화용) — 2026-11-18

`build_city_net.py`. 상·하행을 한 줄로 합친 개요도용 망이다. 방향별 도로 그래프(위 3층 구조)를 대체하지 않는다.

- 선형을 10m 간격으로 촘촘히 한 뒤, 운행횟수가 많은 노선부터 차례로 얹는다. 각 점은 **이전 노선들이 만든 꼭짓점 중 25m 안의 가장 가까운 것**에 붙인다(현재 노선이 방금 만든 점에는 붙지 않음). 이로써 상·하행과 교차로의 몇 m 어긋남이 한 줄로 합쳐진다.
- 연속한 두 점이 붙은 기존 꼭짓점끼리 인접하지 않으면 기존 망에서 최단경로(직선거리 × 1.6 + 30m 이내)를 찾아 그 경로를 쓴다(간이 map matching).
- 간선마다 지나는 계열 집합을 기록하고, 차수가 2가 아니거나 계열 집합이 바뀌는 점에서 끊어 세그먼트로 압축한다.
- 결과(291개 노선): 꼭짓점 67,045개, 간선 67,426개, 세그먼트 1,279개. 계열 수별 길이 — 1개 507km, 2개 148km, 3개 49km, 4개 12km, 5개 9.3km, 6개 2.7km, 7개 1.1km, 8개 2.7km, 9개 0.7km. 7개 이상 겹치는 곳은 온양온천역 ~ 시외버스터미널 일대 4.5km뿐이다.
- 그림(`draw_city_net.py`): 계열(백 단위, 두 자리 공영은 십의 자리 기준, 한 자리·1000번대·순환·심야는 기타)별 색, 겹치는 구간은 계열 수만큼 나란히 그린다(선 하나 2px, 최대 9줄). 오프셋 방향은 세그먼트를 서→동으로 고정해 정해 상·하행이 같은 쪽에 그려진다.

## 7. 계열별 분석 결과 (시내버스, 공영 제외)

### 400번대 상행 — 8개 노선, 구간 21개, 분기 6곳, 합류 6곳

- 가닥: 시외버스터미널(400·430·450·451, 62회) / 신정호관광지(402·404, 26회) / 배방환승정류장(406·407, 14회)
- 본선축: 시외버스터미널 → 온양온천역 → 신창 → 도고 → 군덕복지회관 → 가산2리 가래기 (451번 경로)
- 본선 위 종점: 400·404(신창휴게소 부근), 406·407(순천향대 부근), 450(군덕복지회관)
- 우회 3곳: 상설시장 경유(402·404·406·407, 40회), 배미·모아엘가 쪽(406, 10회), 경희학성·행목리 쪽(402·404·407, 30회)
- 지선 2곳: 순천향대 후문 삼거리 → 오목초(402, 4회), 건널목삼거리 → 신언4리(430, 16회)
- 정류소 그래프에서 분기로 보였던 읍내리까치골의 400 / 430은 도로로 보면 분기가 아니라 단축·연장이다.

## 8. 표기법 아이디어 (UI는 추후 확정)

- **세로 스크롤 스마트폰 화면 전제. 뼈대는 트리로 그린다.**
- **가지끼리 재합류**: 합류 지점에서 운행횟수가 많은 쪽을 부모로 정한다. 들어오는 쪽 가지는 "○○에서 △△번대와 합류" 연결 표시로 끝내고 누르면 그 위치로 이동한다. 받는 쪽 정류소에는 합류 표시를 붙인다. 공유 구간을 양쪽에 복제하는 방식과 두 줄을 나란히 그리는 방식은 접었다.
- **들어갔다 나옴**: 분기로 그리지 않고 본선 옆에 들여 쓴 정류소 묶음과 "일부 노선만 경유" 표시로 처리한다.
- **손님 노선**: 다른 계열 노선을 공유 구간에서만 보여 주고, 떠나는 지점에 "○○ 방면으로 이탈" 표시를 붙인다. 후보는 "도심 밖에서 정류소 몇 개 이상을 연속으로 공유"로 자동 추출하고 관리자가 확정한다(미구현).
- **노선도 배치 프로토타입**: 본선축을 일자로, 가로는 정류소 등간격(우회가 길면 본선을 늘림), 지선은 본선과 만나는 지점보다 북쪽이면 위·남쪽이면 아래. 430 지선은 이 규칙으로 위에 그려지는데 실제로는 본선의 남서쪽이라 기준 재검토가 필요하다.
- 다발형(900번대)은 갈래를 나란히 놓는 별도 표기가 필요하다.
- **시 전체 개요도**(`asan_city_network.svg`): 정류소명·운행횟수 없이 노선망만, 계열별 색, 공통 구간은 여러 색 선을 나란히. 지역 단위 진입 화면 후보.

### 크롤링 JSON 구조 (`raw.json`, 보정본 `fixed.json`)

```
{ "meta": {source, series, crawled_at, weekcd, route_count, errors, retry_log?, shape_fixes?(fixed.json)},
  "routes": [ { "info": {route_id, route_name, route_type, route_direction, st_stop_name, ed_stop_name, alloc_time, ...},
                "series": "4",
                "stops": [ {ord, stop_id, service_id, name, lat, lng, turn_flag} ],
                "turn_ord": "...",
                "shape": [[lat, lng], ...],
                "timetable": [ {ord, departure, weekday, saturday, holiday, vacation} ] } ] }
```

### 도로 그래프 JSON 구조 (`analysis/build_road_graph.py` 출력, 계열별 분석용)

```
{ "nodes":    { id: {lat, lng, in, out} },
  "segments": [ {id, from, to, points, length_m, route_ids, route_names, trips, stops, strands, trunk} ],
  "stops":    { stop_id: {name, lat, lng, segment, offset_m, snap, snap_dist_m} },
  "routes":   { route_id: {name, trips, strand, segment_path, stops} },
  "meta":     {series, direction, routes} }
```

### 시 전체 노선망 JSON 구조 (`build_city_net.py` 출력, 임시)

```
{ "V": [[x_m, y_m], ...],             # 기준점(36.78N, 127.0E) 기준 평면 좌표(m)
  "segments": [ {nodes: [V 인덱스...], groups: ["1","9",...], routes: [노선명...], length_m} ] }
```

3. **방향 판정**: `route_direction` 대신 도심 허브 기준으로 상행·하행을 판정한다.
4. **서비스 구간(방면) 단위 정의**: 번호 계열을 대체할 기본 단위를 어떻게 정의하고 자동 추출할지 정한다. 가장 큰 미결 사항이다.
5. **손님 노선 자동 판정** 구현(도심 구간 제외 기준).
6. **가닥 세분화**(가닥 안의 2차 분류)와 **다발형 계열 판별**.
7. **공영버스 얹기**: 무정차 통과를 급행 지선으로 표현.
8. **등교·일 1회 노선 처리**: 관리자 제외 또는 운행횟수 기준 필터.
9. **들어갔다 나오는 구간과 순환(cycle) 처리**: 그래프가 DAG가 아니다. 노선도 배치 알고리즘은 현재 DAG를 가정한다.
10. **상하행 정류소 짝짓기**(한 화면에 양방향을 그릴 경우).
11. 기존 계열 분석 수치(특히 900번대·800번대)를 보정본으로 재빌드해 갱신.
12. 미분석: 100, 200, 700번대, 1000번 이상 특화 노선, 500번대 계열 구조, 800번대 공영, 대부분 계열의 하행.

### 서비스

13. 실시간 위치를 도로 구간 위에 매핑(차량의 `stop_id` → 노선의 정류소 순서 → 구간과 위치).
14. FastAPI + SSE, React 노선도.
15. 도착정보: `searchBusStopRoute` 활용, 필요 시 구간 소요시간 자체 추정.
16. 관리자 화면(계열·방면 편집, 노선 제외, 손님 노선).

### 확인 필요

- API: `weekcd` 다른 값, 헤더 필수 여부, 호출 제한, `provide_code`·`operation_status`의 다른 값.
- 크롤러는 `(route_ord, ord)`로 정렬하므로 선형 결함은 원본 데이터 문제다. 공식 화면 지도에서도 같은 꼬임이 보이는지 확대해 확인해 볼 만하다.
- 특허 출원을 검토 중이라면 서비스 외부 공개 시점이 신규성에 영향을 줄 수 있다.
